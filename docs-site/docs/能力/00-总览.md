# 总览与选型

## 这批能力是怎么来的

对 5 个毕设项目做横向调研，把"每个项目都在重抄"的东西抽进基座。出现频次（●有 ◐部分 ○无）：

| 能力 | 社团 | 跑腿 | 二手 | 宿舍 | 宠物 | 抽取形态 |
|---|:--:|:--:|:--:|:--:|:--:|---|
| C端账号 + 登录 + 请求/上传/分页 | ● | ● | ● | ○纯Web | ● | 运行时模块 `ruoyi-app` + uni-app 骨架 |
| 站内通知 / 私信 | ● | ● | ● | ◐ | ● | 运行时模块 `ruoyi-message` |
| 支付宝充值 + 钱包对平 | ● | ● | ● | ◐ | ● | 运行时模块 `ruoyi-pay` |
| 媒体上传 | ● | ● | ● | ● | ● | 组件 + 内置接口 |
| 审核状态机 / 看板 / 问卷 / 评价 | ● | ● | ● | ● | ● | 代码模板（`docs/templates/`） |

## 两类形态，别混用

!!! tip "运行时模块 vs 代码模板"
    - **运行时模块**（`ruoyi-app` / `ruoyi-message` / `ruoyi-pay`）：已编译、随基座启动即用，业务模块**依赖它**就能调。
    - **代码模板**（`docs/templates/`）：业务耦合高，不做成运行时模块；是"复制即用"的 DDL + Java 骨架 + 前端片段，复制进你的业务模块改造。

## 落地顺序建议

1. **① C端接入基座** —— 有小程序/H5 就先上；它和媒体上传拼成完整"C 端起步套件"。
2. **② 消息/通知中心** —— 几乎所有系统都要"通知用户 + 未读/已读"。
3. **③④ 支付与钱包** —— 涉及余额/充值/扣款时上，正确性要求最高。
4. **⑤~⑧ 模板** —— 需要审核流/看板/问卷/评价时，复制对应模板。

## 通用集成约定（各模块共用）

- **多租户**：基座 `tenant.enable=true`。登录/无登录上下文时按业务键查库要包 `TenantHelper.ignore(...)`。
- **C 端身份**：C 端用户走 `app_user`，与后台 `sys_user` 靠 Sa-Token loginId 命名空间 `app_user:{id}` 隔离；业务里用 `AppLoginHelper.getUserId()` 拿当前 C 端用户。
- **clientid**：C 端每个请求（含上传）都带同一个 `clientid` 头，值与登录时一致，否则被安全拦截器拒（`-100`）。
- **端口**：基座后端 8199 / plus-ui 8188 / uni-app H5 dev 5188。
