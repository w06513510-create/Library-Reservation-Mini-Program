## 详情

### 1. 媒体上传组件（MediaUpload / VideoView）✅
- **是什么**：业务图/视频的统一上传与展示，采用 **URL 约定**（字段直接存可访问 URL，不走 ossId）。
- **在哪**：
  - 前端：`plus-ui/src/components/MediaUpload/index.vue`（表单侧，`v-model:images` 逗号 URL / `v-model:video` 单 URL）、`plus-ui/src/components/VideoView/index.vue`（只读播放）。
  - 后端：`ruoyi-system` 的 `SysMediaController`（`POST /resource/media/upload`，`@SaCheckLogin`，图 10MB/视频 100MB，返回 `{url,fileName,type}`）。
  - 演示灌数据脚本：`scripts/上传媒体到MinIO_图片视频.py`。
- **怎么用**：表单 `<MediaUpload v-model:images v-model:video>`；详情 `<ImagePreview :src="row.images">` / `<VideoView :src="row.video">`。
- **数据约定**：多图字段存逗号拼接 URL，单值字段存单 URL；前缀要与 `sys_oss_config` 对齐。
- **验证**：端到端通过（多图+视频上传→字段落 MinIO URL→详情展示→MinIO 字节一致）。
- **设计稿**：`docs/specs/2026-07-17-media-upload-components-design.md`。
- **来源**：5 个项目普遍存在。

### 2. ① C 端接入基座（ruoyi-app + uni-app 骨架）✅
- **是什么**：一套"独立于后台 `sys_user` 的 C 端账号 + 登录 + 请求/上传/字典/分页"接入层。任何带小程序/H5 的项目复制即用。
- **在哪（后端 `ruoyi-modules/ruoyi-app`，包 `org.dromara.app`）**：
  - `AppUser`（`app_user` 通用账号表，建表 SQL 在 `ruoyi-app/src/main/resources/sql/app_user.sql`）。
  - `AppLoginHelper`（同一 `StpUtil`，loginId 前缀 `app_user:{id}` 与 sys_user 隔离；`getUserId()` 供业务模块拿当前 C 端用户）。
  - `AppAuthController`（`/app/auth/*`：登录/注册/getInfo/改昵称/改头像/登出 + `wxLogin` 预留桩）。
  - `IAppUserService`、`AppUserVo`（脱敏）、`AppDemoController`（`/app/demo/page` 分页示例，**可删**）。
- **在哪（前端 `uni-app/`）**：`src/utils/request.ts`（clientid+Bearer+401 防抖+silent）、`src/utils/upload.ts`（复用 `/resource/media/upload`）、`src/utils/dict.ts`（本地字典 label/tag 色）、`src/store/auth.ts`、`src/api/auth.ts`、`src/composables/useList.ts`（分页触底/下拉刷新）、页面 `pages/{index,login,mine,demo/list}`。
- **怎么用**：新项目复制 `uni-app/`，改 `src/config.ts`（`BASE_URL`/`CLIENT_ID`）即可对接；业务模块 `@Autowired IAppUserService` 或 `AppLoginHelper.getUserId()` 拿当前 C 端用户。
- **数据/集成约定**：多租户下登录在放行路径无租户上下文 → 查/插 `app_user` 用 `TenantHelper.ignore`；`security.excludes` 只放行 `/app/auth/login`、`/app/auth/register`；每个请求（含上传）带同一 `clientid`。
- **验证**：端到端通过（注册/登录 `app_user:` 命名空间 token / getInfo 脱敏 / 分页 / 未登录 401 / 头像上传→MinIO 字节一致 / 中文 UTF-8 正确 / H5 构建 / Playwright UI 冒烟）。
- **设计稿**：`docs/specs/2026-07-17-app-access-base-design.md`。
- **来源**：有小程序的 4/4 项目各写一遍（宠物/二手用 app_user 独立表；本基座采纳）。

### 3. ② 站内消息/通知中心 ✅（合并点 `60d1564`）
- **是什么**：通用站内**通知** + **私信会话**中心，去业务耦合（通知挂载点统一 `biz_type(varchar)+biz_id(bigint)`）。
- **在哪（后端 `ruoyi-modules/ruoyi-message`，包 `org.dromara.message`）**：
  - `NotificationHelper.send(receiverId, title, content, bizType, bizId)` — **核心复用点**，任意业务触发点一行调用；静默容错（异常只 `log.warn` 不外抛）+ `REQUIRES_NEW` 独立事务（不污染调用方主事务）。
  - 表 `app_notification`（系统通知/未读）、`app_message`（私信，扁平存储、会话按无序对 (from,to) 归并），建表 SQL 在 `ruoyi-message/src/main/resources/sql/`。
  - C 端 `/app/notice/*`（列表/未读数/标已读/全部已读）、`/app/message/*`（会话列表/会话消息分页/发送/未读数），全部 `AppLoginHelper.getUserId()` 强制归属防越权。
  - 管理端 `NotificationController`（`/message/notification/*`，`@SaCheckPermission`）。
- **在哪（前端）**：uni-app `pages/message/{notice,conversations,chat}.vue` + `api/message.ts`（复用 `useList`）；plus-ui `views/message/notification/`。
- **怎么用**：业务里 `NotificationHelper.send(uid, "标题", "内容", "order", 1001L)`；C 端读用 `/app/notice/*`、`/app/message/*`。
- **验证**：端到端通过（私信 A→B：未读=1→会话列表→进入 chat 自动清未读→未读=0；通知：写入→列表→未读=1→标已读→未读=0）；`NotificationHelper.send` 真实发送链路由 `WalletEngineVerifyTest` 覆盖（发送→未读+1→标已读→还原）；全 reactor `mvn compile` + uni-app `build:h5` 通过。
- **设计稿**：`docs/specs/2026-07-18-message-center-design.md`。
- **来源**：5/5 项目都有。

### 4. ③④ 支付宝充值 + 钱包对平 ✅（合并点 `5058c12`）
- **是什么**：与业务无关的**钱包对平引擎** + **支付宝沙箱充值**，绑定 `app_user`。
- **在哪（后端 `ruoyi-modules/ruoyi-pay`，包 `org.dromara.pay`）**：
  - `IWalletService`：`getOrCreate/recharge/deduct/freeze/unfreeze/checkInvariant`——动钱唯一入口；**CAS 防超扣**（`update ... where balance>=?` 影响行数=0 即失败）、**幂等**（`app_fund_flow.idempotent_no` 唯一键 + 动钱前查重）、**对平不变式** `checkInvariant = balance −(Σ入−Σ出)` 恒为 0。
  - 表 `app_wallet`（三层余额 `balance/frozen/total_recharge` + `@Version` 乐观锁）、`app_fund_flow`（append-only 流水）、`app_recharge`（充值单，`out_trade_no` 唯一）；建表 SQL 在 `ruoyi-pay/src/main/resources/sql/pay_wallet.sql`。
  - 支付宝：复用 `ruoyi-common-alipay` 的 `AlipayConfig @ConditionalOnProperty(alipay.app-id)`——**未配 `application-alipay.yml` 不影响应用启动**；未配时 `/app/recharge/simulatePaid` 走 `channel=simulate` 直接到账（充值→对平可在无沙箱凭证下验证）。
  - C 端 `/app/wallet/*`（我的钱包/流水分页/对平校验）、`/app/recharge/*`（create/query/simulatePaid/page），`/app/recharge/notify` 放行（回调）。`deduct/freeze/unfreeze` 仅服务级 API 供业务调用。
- **怎么用**：业务扣款/冻结注入 `IWalletService`；C 端充值走 `/app/recharge/create` →（真实）支付宝表单 / （未配）`simulatePaid`。真钥放 `application-alipay.yml`（已 gitignore，模板见 `.example`）。
- **验证**：端到端通过（充值 100+50→余额 `150.00`、流水 2 条 balance_after 100→150、`checkInvariant=0.00`、未配 Alipay 走 simulate 降级）；全 reactor `mvn compile` 通过。
- **回归测试**：`ruoyi-admin/src/test/java/org/dromara/test/WalletEngineVerifyTest`（`@SpringBootTest`，连真实 DB）——recharge/deduct/freeze/unfreeze 每步对平=0、CAS 超扣被拦、幂等生效；并验证**真实支付宝下单签名**（复用沙箱 `application-alipay.yml`，已 gitignore；未配则该用例自动 `assumeTrue` 跳过）。根 pom `skipTests=true` 默认跳过，`mvn test -pl ruoyi-admin -DskipTests=false -Dtest=WalletEngineVerifyTest` 显式运行；**5 用例通过**。
- **设计稿**：`docs/specs/2026-07-18-pay-wallet-design.md`。
- **已知取舍（见设计稿）**：查单在事务内做网络调用（高并发下连接占用隐患）；对平只覆盖可用余额（frozen 为对手方）；上线前务必换支付宝真钥并配 `application-alipay.yml`。
- **来源**：4/5 项目（宠物对平引擎 + 二手/社团支付宝套路）。

### 5. ⑤~⑧ 复用脚手架/模板 ✅（合并点 `00de725`）
- **是什么**：业务耦合较高、不适合做成运行时模块的能力，做成**"复制即用"代码模板 + 文档**（DDL + Java 骨架 + 前端片段 + README），新项目按需复制到自己的业务模块改造。
- **在哪**：`docs/templates/`（索引见 `docs/templates/README.md`）：
  - `audit-state-machine/` — ⑤ 通用审核单（`biz_audit`+`biz_audit_log` DDL、`BizAuditServiceImpl` 状态机、`AuditCallback` 按 bizType 回调钩子）。
  - `dashboard/` — ⑥ `/overview` 聚合 + echarts 页骨架（Controller/Vo/聚合 Mapper.xml + `index.vue` KPI 卡片+4 图 + api ts）。
  - `survey-engine/` — ⑦ 问卷/测评/考试引擎（`survey`/`survey_question`/`survey_answer`/`survey_record` DDL、`SurveyScoreUtils` 客观题判分、`objective`/`anonymous` 开关统一考试/调查/问卷、Excel 导题）。
  - `rating/` — ⑧ 评价打分（`rating` DDL 一单一评 `uk_biz_role`、`RatingPartyResolver` 服务端定向、plus-ui el-rate 片段、uni-app `StarRate.vue`）。
- **怎么用**：见各子目录 README（复制到哪、改什么、通用 vs 按业务改、自检要点）；占位包名 `org.dromara.<biz>` 全局替换。
- **验证**：docs-only（在 Maven 构建之外，零编译风险）；抽查 README 索引 / 问卷判分 / 审核状态机质量通过，风格对齐 `ruoyi-app`。
- **落地顺序建议**：⑦问卷引擎（宿舍曾抄 3 份，ROI 最高）→ ⑤审核状态机（几乎每个业务都要审批）→ ⑥看板 / ⑧评价（按需）。落地时需手写的业务耦合点：⑤的 `AuditCallback`、⑧的 `RatingPartyResolver`、⑥聚合 SQL 换表列。
- **来源**：审核 5/5、看板 4/5、评价 4/5、问卷（宿舍内部 3 份）。
